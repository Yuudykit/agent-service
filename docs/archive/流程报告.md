## 一、项目目标与验收标准

从零手写一个"技能 + 工具 + 智能体客服"系统，核心对标：

| 技术要求 | 落地模块 |
|---------|---------|
| Function Calling + 工具调用 | `core/agent_loop.py` + `tools/registry.py`（装饰器注册、签名自动推导 schema） |
| RAG | `rag/`（chunker → embedder → build → retriever → reranker 完整管线） |
| 上下文管理 | `core/context.py`（窗口滑动 → token 截断 → 摘要占位三层递进） |
| Agent Memory | `core/memory.py`（会话摘要 + 用户画像 + 持久化） |
| 规划与推理 | `core/reasoning.py`（ReAct：Thought → Action → Observation） |
| Prompt 工程 | `core/prompts.py`（5 层系统提示词，技能层动态生成） |
| 评测/监控 | `eval/eval_script.py`（四指标）+ `tests/test_agent.py`（19 项单测） |

验收成绩：**28/28 评测用例通过（四指标 100%），19/19 单元测试通过**；多轮评测随后扩至 58 用例（hash/bge 双后端 58/58 全绿）。

## 二、数据准备

### 2.1 数据集选型

调研候选：JDDC（京东，推荐）、KdConv（清华）、ATEC+CCKS（微众银行）、CCSE-CS（北航）。
用户选定 **JDDC**：1,025 万段真实京东客服会话，脱敏规范，电商售后场景与目标完全吻合。

### 2.2 下载（踩坑记录）

GitHub 直连不稳定（`git clone`、`codeload` 均失败/超时）。
**解法**：jsdelivr CDN 直连单文件 `https://cdn.jsdelivr.net/gh/SimonJYang/JDDC-Baseline-Seq2Seq@master/data/chat.txt`，39 秒下载 20.8MB。
> 经验：绕过 GitHub 直连问题的可靠降级方案 = CDN 直连单文件。

### 2.3 解析与清洗

`scripts/analyze_jddc.py` —— 解析 7 列 tab 分隔格式，按 session 分组。
**踩坑**：内容列偏移——第 6 列是空列，实际内容在第 7 列。
修复后正确解析：10,943 个会话 / 211,842 条消息 / 平均 19.4 轮每会话。
主题分布：退款 20.6%、退货 18.1%、售后 17.4%、发货 15.8%、快递 14.3%、换货 9.8%、发票 6.5%。

### 2.4 三层数据管线（可复现）

```
scripts/analyze_jddc.py    原始 21 万条消息 → 按会话分组、统计主题
scripts/build_kb_from_jddc.py  全量 10945 会话 → 18,341 条 FAQ 候选（每会话最多取 3 个问答对）
scripts/sample_dialogues.py    筛选 6702 个合格会话 → 均匀采样 120 个完整对话（带主题/轮数/占位符元数据）
scripts/enrich_kb.py       18,341 条候选 → 为 40/47 条 FAQ 抽取真实问法变体（variants）
scripts/build_multiturn_eval.py  120 条会话 → 30 条真实多轮评测用例（history + query）
人工 AI 精炼（Agent做的）         → 47 条结构化 FAQ（11 主题，带 id/问题/答案/关键词/变体）
```

### 2.5 最终数据资产

- `data/kb.json` —— 47 条 FAQ 知识库（核心资产，含 variants 问法变体增强）
- `data/eval_set.json` —— 28 个人工评测用例（含多轮、防幻觉、工具路由）+ `data/eval_multiturn.json` 30 条真实多轮用例（合计 58）
- `data/eval_multiturn.json` —— 30 条真实多轮评测用例（由 dialogues 自动生成，与人工集合并评测）
- `data/dialogues.jsonl` —— 120 个真实完整会话（多轮评测用例的数据源，不再是孤儿数据）
- `data/orders.json` —— 模拟订单（订单查询/退款计算工具用）

## 三、架构设计与实现

```
用户输入 → core/agent_loop.run()（ReAct 循环，max_steps 防死循环）
   ├─ chat()：mock（关键词路由，离线演示）/ 真实（OpenAI 兼容协议调 DeepSeek）
   ├─ tools/registry.execute_tool()：按工具名分发，异常统一捕获为文本
   │     ├─ search_kb          RAG 混合检索（向量 0.6 + 关键词 0.4 → 重排）
   │     ├─ query_info         订单结构化查询（精确查表，NOT_FOUND 明确返回）
   │     ├─ calculate_refund   退款金额计算（订单金额 - 优惠券，质量问题退全款）
   │     └─ transfer_human     转人工（950618 + App 渠道）
   ├─ core/context：消息窗口 → token 截断 → 摘要占位（以完整回合为单位裁剪）
   ├─ core/memory：规则摘要 + 画像抽取（订单号/发票诉求/业务意图）→ 注入 system prompt
   └─ core/prompts：5 层提示词（角色/技能[动态]/规则/few-shot/记忆回顾）
```

### 关键设计决策（面试可讲）

1. **工具注册零配置**：`@register_tool` + `inspect.signature` 自动推导 JSON Schema，
   加工具 = 写函数 + 加一行 import，提示词技能层随之自动更新。
2. **RAG 双通道**：向量通道（特征哈希 bigram，零依赖）+ 关键词通道（业务词精确命中），
   权重 0.6/0.4 可调，互为兜底。
3. **工具结果以文本回填**（Observation 语义）：execute_tool 永不抛异常，
   错误转成 `[工具异常]`/`[NOT_FOUND]` 文本，让模型"看到"失败并决策兜底。
4. **检索置信度**：低分命中明确标注，模型据此判断"没查到 → 转人工"，不编造。

## 四、遇到的问题与排查过程（完整记录）

### 问题 1：mock 模式工具结果回填后死循环

**现象**：工具结果回填后，mock 仍拿旧 user 消息判定"要调工具"→ 循环 3 步耗尽 → 误走兜底。
**根因**：`_mock_chat` 无条件取"最后一条 user 消息"判断，没识别"刚拿到工具结果"的状态。
**修复**：状态机——`messages[-1].role == "tool"` 时模拟模型"阅读结果 → 总结回答"。
**价值**：真实 LLM 看到 tool 结果会自然给最终回答，但 mock 需要显式处理这个状态——这逼真地复刻了 Function Calling 的配对语义。

### 问题 2：monkey-patch 陷阱（P0 阶段）

**现象**：验收脚本 patch `registry.execute_tool` 属性，工具调用记录不到。
**根因**：`agent_loop.py` 里是 `from tools.registry import execute_tool`——绑定的是**模块级名字**（值），patch 类的属性不生效。
**修复**：patch `core.agent_loop.execute_tool`。
**价值**：Python 工程面试高频考点（import 绑定时机），实测命中。

### 问题 3：检索排序被 2-gram 挤掉正确条目

**现象**：「商品缺货要等多久」的正确条目 kb_013 被「保修期是多久」靠 2-gram 重合挤出。
**根因**：kb_013 的 keywords 漏了「缺货」核心词 → 数据质量问题。
**修复**：校准 keywords（数据层修复）。
**价值**：**检索质量 = 数据质量**——这是"数据准备最难"的活体验证，也是 RAG 项目的核心认知。

### 问题 4：特征哈希向量的稀疏性——「退钱」vs「退款」

**现象**：「我想退钱，多久能到？」检索第一是优惠券条目（错误），退款条目分数极低。
**排查过程**：
- 对比实验：带符号哈希 11/14 vs 无符号 10/14（带符号略优，保留）；
- 归因：带符号哈希对稀疏中文会正负相抵；「怎么」这类高频词污染 bigram。
**三层修复**：
1. embedder 加停用词过滤（单字功能词删除 + 双字词整体排除）；
2. search_kb 加口语归一化表（`退钱→退款`）；
3. kb_010 keywords 补录「退钱」「退款」。
**效果**：「退钱」正确命中 kb_010。
**价值**：工程上"近义替换"最终靠数据校准 + 归一化兜底——embedding 不是万能的。

### 问题 5：RAG 检索置信度缺失

**现象**：无关问题（天气）直接调 search_kb 时返回低分无关条目（0.0159），
mock 会照抄第一条导致答非所问。
**分析**：真实 LLM 模式下模型可能对任何问题都尝试调工具，低分结果必须明确提示。
**方案**：在 `search_kb` 输出中标注匹配类型与分数（`匹配:keyword 分:0.33`），
`_mock_chat` 对低置信度走"未找到→转人工"分支，防幻觉链路完整。

### 问题 6：订单号正则过严

**现象**：e_26/e_27/e_28 三个新用例路由失败（走了 search_kb）。
**根因**：mock 路由正则 `\d{12,}` 要求 12 位以上数字，而演示订单号
`JD20260815001` 的数字部分只有 11 位（JD 前缀 + 11 位）。
**修复**：正则改为 `JD\d{8,}|\d{10,}`，同时按语境分流——
含金额语境词（钱/多少/算）→ calculate_refund，否则 → query_info。

### 问题 7：P1 升级引入的回归——检索结果直出

**现象**：多轮演示中回答是原始检索文本（含 `[检索结果]` 前缀和匹配分数），
不是「根据平台规则」的总结。
**根因**：P0 的 search_kb 输出 `  答：`（3 空格），P1 升级时改成 `   答：`（4 空格），
而 `_mock_chat` 按 3 空格匹配 → 总结分支失配 → 原样直出。
**讽刺点**：**评测 28/28 全过但没发现**——关键词断言在原始文本里也能命中。
**修复**：`_mock_chat` 改为 `ln.lstrip().startswith("答：")` 任意缩进匹配，
并新增回归测试 `test_e2e_search_kb_result_summarized` 锁定行为。
**价值**：评测指标设计要关注"行为正确"而非"关键词命中"——这是评测工程的核心教训。

### 问题 8：口语归一化污染向量通道

**现象**：修复问题 7 后 e_12「家电坏了怎么申请售后」检索结果全错
（前 3 条全是退款条目，正确的 kb_026 消失）。
**根因**：`search_kb` 在检索前整体归一化 query（`坏了→质量问题`），
「家电坏了」的 bigram 被改掉，向量通道语义偏移。
**修复**：归一化从"检索前整体替换"改为"仅关键词通道内生效"
（`rag/retriever._normalize_keywords`），向量通道始终用原始 query。
**价值**：**归一化与向量化是两个正交操作，混在一起必然出事**——模块边界划分的教训。

### 问题 9：Memory 规则摘要去重失效（P2 阶段）

**现象**：两条同为"发票"意图的消息，摘要里"用户咨询：发票"出现两次。
**根因**：去重判断 `"咨询"+join not in facts` 比较的是拼接串，
而列表里存的是带"用户咨询："前缀的完整字符串 → 永远不相等。
**修复**：用完整事实串判重。
**价值**：字符串拼接 vs 存储格式不一致的经典低级 bug，测试能抓到。

### 问题 10：企业发票画像抽取不全（Day 8 阶段）

**现象**：「想开增值税专用发票」抽不出 `enterprise_invoice` 画像。
**根因**：正则要求"企业/公司/单位"与"抬头/税号"同现，消息里只说了"增值税专用发票"。
**修复**：规则增强——检测"增值税专用发票/专票/企业发票"同样标记企业开票画像。
**价值**：画像规则要覆盖"业务等价表述"，不能只写最标准的说法。

### 问题 11：评测工具期望值语义不一致（Day 8 阶段）

**现象**：e_15-e_18（fallback 用例）期望 `tool="fallback"`，
而评测逻辑只认 `"none"` 表示"不调工具"。
**修复**：`expects_no_tool = expected_tool in ("none", "fallback")`。
**价值**：测试数据与评测逻辑的契约要显式对齐。
