# 电商售后智能客服 Agent · 项目说明

基于 JDDC 京东客服对话整理了 47 条 FAQ。CLI 和 Web 共用 Function Calling 主循环、混合检索与会话上下文，支持离线 mock 和 DeepSeek API。项目按单机演示设计，运行方式见 [README](../README.md)。

---

## 一、总体架构与数据流向

```
                         ┌────────────────────────────────┐
                         │  入口层                         │
                         │  main.py (CLI)  webapp/server.py│
                         └───────────┬────────────────────┘
                                     │ user_input
                         ┌───────────▼────────────────────┐
   system prompt ◄────────│  推理层 core/                  │
   (五层,含记忆回顾)       │  agent_loop.run() 六步循环      │
                         │  ├─ context.py   消息+回合裁剪   │
                         │  ├─ prompts.py   提示词组装      │
                         │  └─ memory.py    画像记忆        │
                         └───────────┬────────────────────┘
                          tool_calls │ (JSON Schema 声明)
                         ┌───────────▼────────────────────┐
                         │  能力层 tools/                  │
                         │  registry → query_info          │
                         │             calculate_refund    │
                         │             search_kb ──┐       │
                         │             transfer_human      │
                         └────────────────────┼──────┬─────┘
                                              │      │ 工单落盘
                         ┌────────────────────▼──┐ ┌─▼──────────────┐
                         │  知识层 rag/           │ │ data/handoffs/ │
                         │  FAQ 索引→向量+关键词  │ └────────────────┘
                         │  retriever→reranker   │
                         └───────────┬───────────┘
                                     │ 检索结果(文本)
                                    回填 messages → 下一轮循环 → 最终回答
```

**一句话数据流**：用户输入 → 进入 context（可能触发回合裁剪）→ 连同五层 system prompt 发给模型（或 mock 路由器）→ 模型决定是否调工具 → 工具执行（检索/查库/计算/转人工）→ 结果以 `tool` 消息回填 → 循环直到模型给出最终回答 → 回答写回 context 并落盘会话。

## 二、各部件的作用与必要性

### 1. 入口层

**`main.py`（CLI 入口，约 100 行）**
- 作用：命令行交互，`--mock`（离线演示）/ `--verbose`（打印每步 Thought/Action）/ `--memory`（启用记忆）。
- 必要性：面试现场没有 API key 也能演示完整链路——这是 mock 模式存在的根本理由。

**`webapp/server.py`（HTTP 服务，352 行，零依赖标准库 http.server）**
- 作用：把 `run()` 包成 `POST /api/chat`，SSE 流式推送；会话持久化到 `data/sessions/`；两道用量护栏；JSONL 事件日志；bad case 收集；转人工交接包落盘。
- 必要性：真实用户不会用命令行；且"重启后会话不失忆""超预算不烧钱"这两个真实场景只能在服务层做。
- 细节：
  - 会话落盘为 `data/sessions/{session_id}.json`（原子写：先写临时文件再 rename），服务重启后懒加载——测试过重启后用同一 session_id 续聊，历史完整。
  - 护栏两道：日 token 预算（真实模式累计落盘 `data/usage/{日期}.json`，超限直接返回降级话术，**不调 API**）+ 每会话轮次上限（mock 也限，防刷）。
  - 请求用全局锁串行化（`run()` 非线程安全，共享 RAG 索引和 data/）——单机低并发下的正确选择，多实例部署是明确不支持的。

### 2. 推理层

**`core/agent_loop.py`（423 行，项目心脏）**
- 作用：六步主循环——用户输入入栈 → 调模型 → 无 tool_calls 则返回最终回答 → 有则逐个执行工具 → 结果按 `tool_call_id` 回填 → 回到调模型，直到无调用或超过 `max_steps=3`（防死循环）。
- 双模式分叉点：
  - **mock**：`_mock_chat` 用关键词路由状态机模拟模型判断，零 token、零依赖；
  - **真实**：OpenAI 兼容协议调 DeepSeek（`tools=schema` 传入 function calling）。
- 健壮性细节：
  - 真实调用设置 60 秒超时，对限流、部分服务端错误和连接错误退避重试。Web 入口捕获最终异常并返回降级话术。
  - `on_event` 回调向前端推三类事件：`tool`（工具调用状态）、`delta`（流式文本增量）、`usage`（token 用量）。
  - 流式模式下 tool_calls 的 arguments 是分片到达的，需要聚合后才能 `json.loads`——这是实测验证过的坑点。
- 必要性：所有其他部件都挂在这个循环上。手写它（而不是用 LangChain）的意义：**知道 messages 数组的配对规则、知道循环终止条件、知道每一步哪里会坏**。

**`core/context.py`（185 行）**
- 作用：messages 数组管理 + 上下文窗口裁剪。
- 细节：以回合为单位裁剪，保留同一回合内的 assistant 工具请求与 tool 结果配对。token 数使用字符近似估算。
- 必要性：无裁剪则长会话必然爆上下文；裁剪单位选错则直接 API 报错。

**`core/prompts.py`（99 行）**
- 作用：五层分层系统提示词，从稳定到易变：
  1. 角色定义（稳定）——京东售后客服"小帮"
  2. **技能说明（动态生成）**——遍历工具注册表自动拼装，加工具即自动生效
  3. 行为规则（稳定）——只依据检索结果回答、检索不到就说没查到、不编造政策
  4. few-shot（2 个正例 + 1 个边界例）
  5. 记忆回顾（每次会话动态注入，来自 memory.recall()）
- 必要性：第 2 层的动态生成解决了"工具加了但提示词没告诉模型"的脱节问题——这是这个项目里最接近"skill 按需注入"思想的设计：**上下文里永远只放当前实际可用的能力描述**。
- 防幻觉的核心机制在第 3 层规则 + few-shot 的边界例（天气问题拒答），配合工具返回"没查到"时的兜底话术形成双保险。

**`core/reasoning.py`（132 行）**
- 作用：ReAct 文本协议解析器——从模型输出里提取 `Thought/Action/Final Answer`。
- 目前作为独立组件保留并测试。主循环使用结构化 `tool_calls`，mock 的 verbose 轨迹由规则路由器生成。

**`core/memory.py`（189 行）**
- 主链路从用户发言提取订单号、售后意图和企业发票需求。CLI 使用 `data/memory.json`，Web 按会话使用 `data/memory/{session_id}.json`。
- 当前指代主要依赖近期消息。超窗压缩使用截取原文的摘要占位，`Memory.summarize()` 提供的规则和 LLM 摘要接口尚未接入该流程。

### 3. 能力层（工具）

**`tools/registry.py`（143 行）**
- 作用：`@register_tool` 装饰器在 **import 瞬间**把函数签名/docstring 推导成 JSON Schema 并注册。工具加载顺序即 import 顺序：query_info → calculate_refund → transfer_human → search_kb。
- 必要性：JSON Schema 是 function calling 的合同文本；手写 schema 必然和函数实现漂移，从签名推导则永远一致。这也是"加工具 = 写一个文件 = 全链路（schema、提示词技能段）自动生效"的机制基础。

**四个工具的分工逻辑**（这是设计上有意识的选择）：

| 工具 | 处理哪类信息 | 为什么单独成工具 |
|------|------------|----------------|
| `query_info` | 结构化事实（订单状态） | 精确查询，不该走语义检索——订单号是键值对不是语义 |
| `calculate_refund` | 确定性计算（退款金额） | 算术不能交给 LLM 生成，必须代码算 |
| `search_kb` | 非结构化知识（政策/时效） | 语义模糊、文本量大，正是 RAG 的领域 |
| `transfer_human` | 流程边界（机器搞不定的） | 兜底出口，且要生成交接包 |

这个分类本身是面试要点：**"事实查库、计算用代码、知识走检索、边界转人工"——每一类信息用最适合它的机制处理，而不是全塞给模型**。

**`tools/fallback.py`（184 行）**
- 作用：兜底话术 + 转人工。转人工时会生成**交接包**：从会话上下文里规则抽取（正则+关键词表）订单号、话题类型、情绪标记（如"激动（含投诉倾向）"）、最近 N 轮对话，落盘 `data/handoffs/{工单号}.json`，用户侧同时拿到工单号。
- 设计理由：机器到人的交接质量是真实客服系统的核心环节——人工坐席接手前需要"这单已经发生了什么"的压缩包。槽位抽取用纯规则而非 LLM：**高频路径不值得每次花 token**。

### 4. 知识层（RAG 管线，rag/）

**`embedder.py`（约 240 行）**——多后端 embedding 分发（环境变量 `EMBEDDER_BACKEND` 切换）：
- `hash`（默认）：零依赖特征哈希——中文相邻两字 bigram → 停用词过滤 → 每个 bigram 用 `zlib.crc32` 哈希到 512 维（位置, 符号）→ TF 加权 → L2 归一化。
- `bge`（推荐）：bge-small-zh-v1.5，512 维与 hash 一致，切换零改动；`bge-m3` 1024 维需重建索引；`dashscope` 走云端 API。
- 本地模型从 ModelScope 下载（`models/modelscope/`，自动本地优先）；索引按后端分文件（`kb_index_{backend}.json`）互不覆盖。
- 默认 hash 允许在标准库环境中离线运行。BGE 的对比结果见 [Embedding 选型报告](embedding选型报告.md)的 7 条样本实验。

**`retriever.py`（136 行）**——混合检索：
- `score = 0.6 × 向量余弦 + 0.4 × 关键词命中`，双通道各自打分后加权。
- 关键词通道内做了口语归一化（"坏了"→"质量问题"），且**归一化只作用于关键词通道**，不改写原始 query——早期版本整体替换 query 导致向量通道语义被污染，正确的 kb 条目掉出 top-k，这是实测踩过的 bug。

**`reranker.py`** 按双通道命中、弱匹配和问句片段命中调整分数。

**`chunker.py`** 提供独立的段落和句子切分工具。当前 FAQ 索引直接按条目构建。

**`build.py`（80 行）**——kb.json → `kb_index_{backend}.json` 索引缓存（每条 FAQ 预计算向量），改了知识库要重跑；索引是派生产物**不入库**，首次运行自动重建。

### 5. 数据与数据漏斗（scripts/）

真实数据规模（全部实测统计）：

```
data/raw/jddc_chat.txt   212,808 行消息 / 10,945 个唯一会话（20.8MB）
   ↓ scripts/build_kb_from_jddc.py（全量跑）
   候选 FAQ 18,341 条（其中"其他"噪声类 8,294 条）
   ↓ 人工挑选改写
data/kb.json             47 条标准 FAQ（知识库本体）
   ↓ rag/build.py
data/kb_index_{hash,bge}.json  预计算向量索引（build.py 生成，不入库）
```

- `max_per_session=3` 是唯一闸门（每会话只取前 3 个问答对，防长会话刷屏候选池）；`--max-sessions` 默认全量（10,945 会话 → 18,341 候选）。
- **47 条是设计而非缺陷**：候选池是原料，知识库是人工校准的成品。在特征哈希这种弱向量下，47 条精炼 FAQ 的检索精度高于把上万条噪声直接灌库。
- `data/orders.json`：模拟订单库（含 JD20260815001 等），供 query_info 查询。
- `data/eval_set.json`：28 个人工评测用例 + `data/eval_multiturn.json` 30 条真实多轮用例（合计 58）。

### 6. 质量层

- **`eval/eval_script.py`** 运行 58 条 mock 回归，检查期望工具是否出现以及最终回答的关键词。其中 30 条用例由真实客服会话自动生成。
- **`tests/test_agent.py`** 有 24 项 pytest 测试，覆盖上下文、工具注册、检索、记忆、客户端和部分端到端路径。
- **`scripts/run_real_eval.py`** 执行真实模式冒烟。历史记录覆盖 5 个场景、6 个回合，共 12 次 API 调用和 18,793 tokens。
- **`.github/workflows/ci.yml`** 自动运行测试与 mock 回归。回归用例失败时脚本以非零状态退出。
- **bad case 收集**记录降级、转人工和匹配到兜底话术的事件。`data/bad_cases.jsonl` 保存问题前缀、触发原因、工具列表等字段。
- **日志**：`logs/events.jsonl` 一行一轮（时间戳/会话/模式/工具链/token/延迟/降级标记）。

## 三、一次对话的完整数据流（真实模式）

以「订单 JD20260815001 到哪了」为例：

1. **启动时**：`import tools` 触发装饰器注册 4 个工具（schema 生成）→ `rag` 加载 `kb_index_{backend}.json`（47 条预计算向量）→ `prompts` 组装五层 system prompt（技能段从注册表拼出）。
2. **请求进来**：server 检查护栏（预算/轮次，超限直接降级返回）→ 取/恢复会话 → 调 `run()`。
3. **循环第 1 轮**：context.append(user 消息，触发回合裁剪检查) → 连 system prompt 发给 DeepSeek（`tools=4 个 schema`）→ 模型返回 `tool_calls: [query_info(entity="JD20260815001")]` → server 推 `tool` 事件给前端（"查询订单信息…"）。
4. **工具执行**：query_info 读 orders.json 精确匹配 → 返回「已发货/已揽收/预计 8-18 送达」→ 以 `tool` 消息（带 `tool_call_id`）回填 messages。
5. **循环第 2 轮**：模型读到工具结果，生成最终回答 → **流式**逐字推给前端（delta 事件）→ 完整回答写回 context → 会话落盘 → 日志一行。
6. **若用户接着说「那个订单能退多少钱」**：模型从 messages 历史里解析指代（这就是多轮上下文的意义），调 calculate_refund → 质量问题退全款的规则计算 → 回答。

mock 模式的分叉在第 3 步：`_mock_chat` 用关键词路由选工具，**它不读上下文历史**——所以 mock 下多轮指代会路由错（这是已知且记录在案的 mock/真实行为差异）。

## 四、关键设计取舍（为什么这么做）

| 决策 | 理由 | 代价 |
|------|------|------|
| 手写核心而非 LangChain | 要知道循环/裁剪/配对规则每一处怎么坏；500 行能读懂的就是好的 | 失去生态（无 tracing UI、无现成 reranker） |
| 默认 mock 与 hash 走标准库 | 准备本地配置后即可离线演示 | 路由和字符相似度的泛化有限 |
| mock/真实双模式 | 离线可开发可评测，CI 零成本 | 两套判断逻辑，mock ≠ 真实行为（见不足） |
| 47 条人工整理的 FAQ | 控制候选噪声，方便检查每条政策 | 覆盖面较窄，库外问题仍可能召回弱匹配 |
| 转人工槽位纯规则 | 高频路径不花 token，延迟零 | 泛化有限 |
| 会话存本地 JSON 文件 | 零运维，够单机演示 | 无法多实例，无并发写保护 |

## 五、当前方案的不足

**特征哈希的上限（已用 bge 补上）**
- 「退钱」vs「退款」余弦相似度实测仅 0.047，当时靠停用词表 + 口语归一化表 + 知识库关键词补丁三层救回。本质问题是字符 bigram 没有语义概念，任何没见过的同义表达都可能漏检。
- 2026-08-27 已落地真实 embedding（`EMBEDDER_BACKEND=bge`，bge-small-zh-v1.5，512 维）：纯向量裸考压测 hash 4/7 vs bge 5/7，且 hash 漂到完全无关条目（开票/保质期），bge 错也在语义相邻条目（配送地址/退款去向）。详见 `docs/embedding选型报告.md`。

**mock 与真实模式行为不一致**
- mock 路由器是关键词状态机，不读上下文——多轮指代在 mock 下会错路由（实测：「那个订单能退多少钱」检索出不相关的拆分条款）。这意味着**58 用例评测证明的是 mock 的行为，不是 DeepSeek 的行为**；真实模式只有 5 问的手工验证。CI 绿灯 ≠ 真实链路无回归。

**reranker 是规则不是模型**
- 订单号、时效词加权能救特定 case，但对语义相关性的重排没有贡献。名称里有"rerank"容易让人高估它。

**Agent 循环通过全局锁串行执行**
- QPS 上限约等于一次 agent 循环的耗时（真实模式 5-10 秒）。会话/用量文件无并发写保护，多实例部署会竞态。作为演示够用，作为服务不够。

**转人工交接包没有消费方**
- 工单落盘了，但没有对接任何人工坐席系统——交接协议的上半场（打包）做了，下半场（派单/接起）不存在。情绪标记规则也偏粗糙（关键词命中即"激动"）。

**摘要与画像的覆盖范围**
- 超窗摘要保留原文片段，画像仅提取少量业务信息。独立的 LLM 摘要接口仍待接入主流程。

**评测方法本身的局限**
- 关键词断言会把"语义正确但措辞不同"的回答判为失败（C5 用例踩过：回答正确但期望词「状态」未逐字出现，只能校准期望词）。多轮用例已扩至 32 个（2 手写 + 30 真实会话反哺），bad case 收集目前只认兜底标记，不识别"答了但答错"。

**安全面基本裸奔**
- 无用户认证，session_id 可伪造；除 API key 外没有做任何输入消毒；服务暴露公网时护栏防的是钱包，不是攻击。

**数据利用率的取舍**
- 10,945 个会话已全量用于 FAQ 候选抽取（18,341 条，`--max-sessions` 默认全量）；知识库只覆盖售后高频场景。扩量路径（候选聚类去重）已明确未执行；embedding 已从 hash 升级为 bge。

## 开发与维护

### 配置和依赖

CLI 和 Web 优先读取根目录下的 `config.json`。未创建本地配置时使用 [config.example.json](../config.example.json)，其中 `api_key` 为空。`api_key`、`base_url` 和 `model` 用于真实模型调用。`max_context_tokens` 和 `max_react_steps` 作用于两种入口，`daily_token_budget` 和 `max_turns_per_session` 作用于 Web。检索后端由 `EMBEDDER_BACKEND` 环境变量选择，默认 `hash`。

| 用途 | 安装命令 |
| --- | --- |
| 默认 mock 和 hash | Python 3.12 标准库即可运行 |

### 改动后的验证

| 改动 | 验证方式 |
| --- | --- |
| 更新 `data/kb.json` | `python -m rag.build` 重建对应后端索引。已启动的 Web 服务需要重启以重新加载索引。 |
| 修改工具、会话或 Web 服务 | `python -m pytest tests/ -q`，再运行 `python -m eval.eval_script`。 |
| 修改真实模型调用 | 配置 API Key 后运行 `python scripts/run_real_eval.py --only C1`，或去掉 `--only C1` 跑全部 5 个冒烟场景。 |

[CI](../.github/workflows/ci.yml)固定使用 `hash` 并在未创建本地配置的环境运行。完整 mock 回归读取 `data/eval_set.json` 和 `data/eval_multiturn.json`，缺文件或有断言失败都会返回非零退出码。`scripts/run_eval_p0.py` 保留早期 28 条验收入口。

### 数据文件

`data/kb.json`、`data/orders.json` 和两份回归数据用于运行及验证。`data/dialogues.jsonl` 是数据准备脚本所用的会话样本。`data/raw/` 和 `data/intermediate/` 存放原始数据和候选产物。派生索引、下载模型、`config.json`、会话、交接记录、画像和日志的忽略规则见 [.gitignore](../.gitignore)。

### 运行监控

每个 Web 会话请求分配一个 `request_id`，随 SSE 事件返回。服务端将模式、服务、结束状态、总耗时、等锁时间、首段文本耗时、工具顺序和上报的 token 写入 `logs/events.jsonl`。反馈写入 `logs/feedback.jsonl`，同一请求按最后一次评价汇总。看板 API 返回结构化摘要，保留原文和详细异常的本地日志由维护者直接查看。

| 指标 | 口径 |
| --- | --- |
| 回复返回率 | 发送结束帧的请求数 ÷ 已记录请求数。正常回复、异常降级和护栏拦截各自计数。连接中断按服务端检测结果记录。 |
| P95 总耗时 | 对返回结束帧的请求按服务端耗时排序，取第 95 百分位。 |
| 有帮助率 | 有帮助数 ÷ 已评价回复数。反馈率为已评价回复数 ÷ 已返回回复数。 |

看板支持按离线/真实模式和服务类型筛选，最多汇总最近 2,000 条带请求编号的事件。早期日志保留在原文件中。实际稳定性和满意度需要分模式积累足够样本。
